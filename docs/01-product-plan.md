## 0. 이 문서의 목적

이 문서는 Argos를 **무엇을, 누구를 위해, 어디까지, 어떤 품질로** 만들지 정한다. 어떻게 만들지는 02 아키텍처와 10번대 설계 문서, 언제 끝난 것으로 볼지는 03 완성 기준, 지금 무엇을 할지는 04 작업 지시서에 둔다.

Argos는 **오픈소스(Apache-2.0)로 모두에게 무료로 공개**한다. 영업·가격·라이선스 키·에디션 같은 사업 요소는 존재하지 않으며 이 문서에서 다루지 않는다. "상용 SW 수준"은 사업 모델이 아니라 **품질 기준**이다. 그 기준은 추상적인 말이 아니라 **참조 제품(Datadog APM, Jennifer, Prometheus + Grafana + Alertmanager)이 실제로 하는 것**으로 정의하며, 기능별 기준은 05 문서의 벤치마크 매트릭스에, 완성도의 판정 기준은 03 문서 Gate 2에, 보안 기준은 06 문서의 SEC 요구에 적는다.

개발 방식이 특수하다. 구현은 Claude Code가 하고, 사람은 기획·결정·수락 검수·사내 테스트 환경 운영을 맡는다. 그래서 이 문서는 "읽고 이해하는 문서"가 아니라 **그대로 주문할 수 있는 사양**이어야 한다. 모호한 문장은 AI가 그럴듯한 미완성을 만들게 하므로, 모든 요구를 측정 가능한 형태로 적고 식별자(F-, N-, D-, S-, SEC-, O-)를 부여한다.

## 2. 배경과 제품 목표

### 2.1 현장의 문제

- Java 백엔드 운영팀은 장애가 나면 "어느 요청이, 어느 SQL이나 외부 호출에서, 왜 느렸나"를 분 단위로 찾아야 한다.
- 기존 도구는 셋 중 하나다. 비싸고 무거운 상용, 개발이 멈춘 오픈소스(Scouter), 저장소 운영 부담이 큰 오픈소스(Pinpoint의 HBase).
- 폐쇄망·온프렘 환경이 많아 SaaS형 도구는 쓸 수 없는 곳이 많다.
- Spring Boot 3.x(jakarta), Java 17/21, 가상 스레드, 컨테이너 전환이 진행되면서 구형 APM의 호환성 문제가 늘고 있다.
- 활발히 유지되는, 국내 운영 관행(XLog·액티브 트랜잭션) 기반의 오픈소스 APM이 없다. Argos는 이 빈자리를 오픈소스로 메운다.

### 2.2 제품 목표: "잘 만든 APM"의 정의

1. **앱을 절대 해치지 않는다.** 에이전트 때문에 앱이 느려지거나 죽거나 동작이 바뀌는 일이 없다. 수집 서버가 죽어도 앱은 모른다.
2. **빠뜨리지 않는다.** 제외 규칙에 걸리지 않은 모든 요청이 XLog에 점으로 남는다. 샘플링은 상세 프로파일에만 적용하고, 샘플링·드롭·결측·수집 중단은 숨기지 않는다.
3. **원인까지 3클릭.** 알림 → XLog 드래그 → 트랜잭션 상세에서 SQL·외부 호출·커넥션 대기·메서드 단위 원인이 보인다.
4. **1대로 시작하고 5분 안에 본다.** 서버 1 + ClickHouse 1 + PostgreSQL 1. `docker compose --profile demo up` 한 번에 샘플 트래픽까지 뜬다. 인터넷 없이 설치된다.
5. **운영자가 믿을 수 있는 숫자.** 대시보드의 TPS, XLog의 점 수, 서비스 통계의 건수가 서로 일치한다. SQL 통계는 샘플이 아니라 전수다. 시계 차이·드롭·결측이 있으면 표시한다.
6. **개인정보는 기본적으로 수집하지 않는다.** 바인드 파라미터·쿼리스트링·사용자 식별자·예외 메시지 속 개인정보는 설정 없이 마스킹되거나 수집되지 않는다. 운영자가 명시적으로 켜야만 수집된다.

### 2.3 AI 주도 개발이라는 전제가 바꾸는 것

- **가능해진 것**: 에이전트·서버·UI 세 영역을 소수 인원으로 병행 개발. 반복적인 계측 모듈(HTTP 클라이언트 6종, DB 드라이버 9종)을 빠르게 양산.
- **더 중요해진 것**: 완성 기준의 명확성, 자동화된 검증(호환성 매트릭스, 오버헤드 벤치, 정확성 정합 검사, 보안 테스트, E2E), 사람의 수락 검수. AI가 "동작한다"고 보고해도 테스트가 증명하지 않으면 끝난 것이 아니다.
- **사람이 여전히 해야 하는 것**: 제품 결정, 수락 테스트, 사내 환경 운영, 핵심 경로 코드 리뷰, 실환경 적용 판단, 외부 PR 승인, 보안 신고 대응.

## 5. 제품 정의

### 5.1 한 줄 정의

Argos는 Java 백엔드를 위한 오픈소스 설치형 APM으로, 모든 트랜잭션을 100% 기록하고(XLog) 느린 요청의 원인을 SQL·외부 호출·커넥션 대기·메서드 단위로 보여주며, 여러 서비스에 걸친 요청을 하나의 트레이스로 잇는다.

### 5.2 제품 품질 원칙

모든 설계·구현 결정은 아래 원칙에 비추어 판단한다. 충돌하면 위에 있는 것이 이긴다.

| 순위 | 원칙 | 구체적 의미 |
|---|---|---|
| 1 | 안전성 | 에이전트는 앱 스레드를 블로킹하지 않고, 예외·반환값을 바꾸지 않고, 객체 동일성을 깨지 않고(Runnable 래핑 금지), 상한 없는 메모리를 쓰지 않는다. 초기화 실패도 앱 기동을 막지 않는다 |
| 2 | 정확성 | 수집한 숫자는 서로 일치하고 재현 가능하다(7.1). 1요청 = 1트랜잭션, 1 SQL 실행 = 1 step. 드롭·결측·샘플링·시계 차이·수집 중단은 숨기지 않고 표시한다 |
| 3 | 프라이버시 기본값 | 개인정보 가능 필드는 설정 없이는 수집되지 않거나 마스킹된다. 원격으로 수집 범위를 넓힐 수 없다(06 문서) |
| 4 | 즉시성 | 요청이 끝나고 5초 안에 XLog와 대시보드에 보인다. XLog 점은 1초 안에 흐른다. 액티브 트랜잭션은 5초 주기로 갱신된다 |
| 5 | 단순성 | 런타임 구성 요소는 넷(에이전트, 서버, ClickHouse, PostgreSQL). 설정 없이 기본값만으로 의미 있는 화면과 기본 알림이 나온다 |
| 6 | 호환성 | 8장 매트릭스 전부에서 동작하며, 매트릭스는 CI가 매일 검증한다. 비지원 환경은 문서에 명시한다 |
| 7 | 사용성 | 운영자가 교육 없이 전체 현황 → XLog → 상세까지 간다. 모든 목록은 상세로, 모든 상세는 관련 통계로, 모든 값은 필터로 이어진다 |

### 5.3 제품 방향 결정

### 5.4 용어

| 용어 | 정의 |
|---|---|
| Application(앱) | 같은 코드를 실행하는 인스턴스의 논리 그룹. 식별자는 **(이름, 환경)** 쌍. 예: `order-api` / `prod` |
| Environment(환경) | `app.env` 태그. prod·stg·dev 등 자유 문자열. 모든 목록·알림 규칙·전체 현황의 필터 기준 |
| Instance(인스턴스) | 에이전트가 붙은 JVM 1개. 설정 이름 우선, 없으면 `host:port`(포트 확정 후), 폴백 `host:pid` |
| Transaction(트랜잭션) | 요청 또는 배치 작업 1건의 처리. XLog의 점 1개. 종류(kind)는 HTTP / BATCH / MESSAGE(1.x) |
| Service(서비스) | 트랜잭션의 분류 이름. HTTP는 URL 패턴(`GET /api/orders/{id}`), 배치는 `BATCH <Job.Step>` |
| Profile(프로파일) | 트랜잭션 내부의 단계(step) 목록. 종류: SQL, DBC(커넥션 대기), COMMIT/ROLLBACK, HTTP, METHOD, ASYNC, ERROR, STACK, MESSAGE |
| Trace(트레이스) | 여러 인스턴스에 걸친 트랜잭션들을 `trace_id`로 묶은 것 |
| XLog | 시간(x)·응답시간(y) 산점도. 제외 규칙에 걸리지 않은 트랜잭션 전수를 표시 |
| Active Transaction | 지금 처리 중인(끝나지 않은) 트랜잭션 |
| Counter(카운터) | 주기적으로 수집하는 수치. TPS, 응답시간, 힙, GC, 스레드, 풀 등. gauge 또는 counter 종류를 가진다 |
| 에러 그룹 | 예외 클래스 + 마스킹된 메시지 패턴 + 최상위 앱 프레임으로 묶은 에러의 지문 |
| 수집 상태 | 에이전트·서버 드롭, 제외 요청 수, 적재 지연, 시계 차이, 수집 중단 구간을 모은 패널 |

### 5.6 핵심 사용 시나리오

화면·데이터·알림 설계는 아래 시나리오를 만족하는 방향으로 한다. 각 시나리오는 그대로 수락 테스트 시나리오가 된다.

| ID | 상황 | 사용자 행동 | 필요한 화면·데이터 | 성공 기준 |
|---|---|---|---|---|
| S-01 응답 지연 장애 | 특정 서비스 p95가 임계치를 넘었다는 알림 | 알림 딥링크 → 대시보드에서 시점 확인 → XLog에서 느린 점 드래그 → 선택 영역 요약에서 공통 서비스 확인 → 상세에서 SQL step이 시간 대부분을 차지함을 확인 → SQL 통계에서 추이 확인 | 대시보드, XLog(선택 요약), 트랜잭션 목록·상세, SQL 통계 | 알림 수신 후 화면 전환 5회 이내, 10분 이내 원인 SQL 식별 |
| S-02 요청 적체 | 액티브 트랜잭션 수가 급증 | 액티브 화면에서 오래 걸린 요청 확인(상태: SQL 실행 중/외부 호출 중/커넥션 대기) → 해당 스레드 스택 보기 또는 인스턴스 스레드 덤프 → 락 대기 스레드 확인 | 액티브 트랜잭션, 단일 스레드 스택, 스레드 덤프 뷰어 | 덤프 요청 후 30초 내 화면 표시, 스레드 상태별 그룹, 진행 중 트랜잭션과 스레드 매칭 |
| S-03 느린 SQL 튜닝 | 개발자가 어제 하루 가장 비싼 SQL을 찾는다 | SQL 통계 Top N(총 시간, 전수) → SQL 상세 추이 → 실행 서비스 목록 → 관련 트랜잭션 → 같은 SQL이 한 요청에서 수백 번 실행됨(N+1) 확인 | SQL 통계(전수 집계), SQL 상세, 트랜잭션 상세(반복 step 접기) | 1일 범위 Top N 조회 1초 이내, 총 시간·횟수가 전수 기준(D-12), 반복 step은 접힌 요약 |
| S-04 배포 후 회귀 | 배포 뒤 특정 서비스가 느려졌다는 의심 | 대시보드의 배포 마커로 시점 확인 → 서비스 통계를 버전별로 분리해 응답시간 증가 서비스 식별 → 상세에서 새로 추가된 외부 호출 확인 | 배포 마커(F-S18), 버전 태그(F-A21), 서비스 통계 버전 분리, 트랜잭션 상세 | 배포 전후 버전의 p95가 한 표에서 비교됨. 두 기간 한 화면 비교(F-U12)는 1.x |
| S-05 분산 호출 지연 | `order-api`가 느린데 자기 SQL은 빠르다 | 트랜잭션 상세의 HTTP step → 트레이스 뷰에서 `payment-api` 구간이 지연 → 그 인스턴스 대시보드로 점프 | 트레이스 뷰, 인스턴스 간 이동 | 2-hop 트레이스가 하나의 트리로 표시, 각 구간과 "네트워크·대기" 차이 표시 |
| S-06 메모리·GC 문제 | 힙 사용 추세가 오르고 GC 정지 시간이 늘어난다는 알림 | 인스턴스 상세에서 힙·GC 차트 확인 → 스레드 덤프 → 재시작 여부 판단 | 인스턴스 상세, 알림 규칙(GC pause 시간) | 7일 범위 힙 추세가 1초 내 표시, ZGC·Shenandoah에서 동시 사이클이 정지 시간으로 오인되지 않음(D-25) |
| S-07 에이전트 도입 | 운영자가 새 앱에 에이전트를 붙인다 | `--check`로 사전 점검(연결·토큰·TLS·시계·JDK·호환성) → 관리 화면에서 앱(환경) 등록·토큰 발급 → 인스턴스 1대에 jar + yml + `-javaagent` → 재기동 → 접속 확인 → 인스턴스 비교 표에서 미적용 인스턴스와 CPU·p99 비교 → 자가 진단에서 드롭 0·모듈 자동 비활성 0 → 확대 | 사전 점검 명령(F-A27), 관리 화면, 인스턴스 비교 표(F-U20), 자가 진단 | 사전 점검 실패 항목 0, 절차 10분 이내, 앱 로그 에이전트 ERROR 0·stdout 출력 0, 카나리 CPU 차이 3%p 이내·p99 차이 1ms 이내 |
| S-08 수집 서버 장애 | 수집 서버가 내려갔다(장애 또는 계획 정지) | 아무것도 안 함 | 에이전트 재접속, 드롭 카운터, 수집 중단 구간 표시(D-18) | 앱 응답시간 변화 없음, 복구 후 1분 내 재접속, 유실 수가 수집 상태 패널에 표시되고 중단 구간이 차트에 음영으로 보여 TPS 0과 구분된다 |
| S-09 배치 작업 지연 | 새벽 정산 `@Scheduled` 작업이 평소 10분인데 1시간째 실행 중이고, 같은 DB를 쓰는 HTTP 서비스가 느려졌다 | 전체 현황의 "진행 중 배치" 확인 → 액티브 트랜잭션(종류=배치)에서 경과 시간 확인 → 스레드 스택 → SQL 통계(종류=배치)에서 그 작업의 SQL 추이 | 트랜잭션 종류 필터, 액티브 트랜잭션, 단일 스레드 스택, SQL 통계 | 배치 트랜잭션이 XLog·액티브·SQL 통계에 HTTP와 구분되어 보인다. HTTP 서비스 통계·Apdex·TPS는 배치의 영향을 받지 않는다(D-20) |
| S-10 커넥션 풀 고갈 | 특정 인스턴스에서 응답시간이 일제히 느려졌고 "Connection is not available" 에러 | 알림(풀 대기 수) → 인스턴스 상세에서 풀 active=max·pending 상승 확인 → 액티브에서 커넥션을 오래 쥔 요청 식별 → 상세에서 커넥션 획득 대기 step과 긴 SQL step 구분 | 풀 메트릭(F-A10), 알림 지표 `jdbc_pool_waiting`, DBC step(F-A03), 액티브 트랜잭션 | 상세에서 "커넥션 대기 N초 + SQL M초"가 분리되어 보인다. 풀 대기 알림이 조건 충족 후 30초 내 도착(N-23) |
| S-11 외부 API 타임아웃 폭주 | PG사 API가 응답하지 않아 결제 요청이 30초씩 걸리고 Tomcat 스레드가 바닥난다. PG사에는 에이전트가 없다 | 알림(외부 호스트 타임아웃 비율) → 외부 호출 통계에서 호스트별 p95·타임아웃 수 급증 → 호출 서비스 목록 → 액티브(상태=외부 호출 중, 호스트) → 대시보드 Tomcat 스레드 사용률 | 외부 호출 통계(호스트별, 전수), HTTP step 실패 분류(TIMEOUT/CONNECT_FAIL), 액티브 상태, Tomcat 스레드 메트릭 | 피호출자에 에이전트가 없어도 호스트 단위로 원인이 식별된다. 타임아웃이 일반 에러·5xx와 구분되어 집계된다 |
| S-12 특정 사용자·요청 추적 | 고객센터에서 "사용자 A가 14:03경 결제 실패" 문의 | 전역 검색에 사용자 ID(해시 모드면 입력값 해시) + 시간 범위 → 트랜잭션 목록 → 에러 트랜잭션 상세 → 에러 스택·SQL → trace id로 외부 로그 시스템 열기 | user_id·request_id 검색(기간 필수), 트랜잭션 상세, 외부 로그 링크(F-U18) | 1시간 범위 사용자 ID 검색 3초 이내(N-24). 상세에서 로그 시스템으로 클릭 한 번. 사용자 식별자 수집이 꺼져 있으면 그 사실을 안내 |

## 6. 기능 범위

## 7. 비기능 요구사항 (NFR)

### 7.1 데이터 정확성 요구

"운영자가 믿을 수 있는 숫자"를 위한 규칙이다. 위반은 버그로 취급하고, 각 규칙은 자동 테스트로 고정한다(03 문서).

| ID | 규칙 |
|---|---|
| D-01 | 트랜잭션 응답시간은 단조 시계(`System.nanoTime`) 차분으로 잰다. 벽시계 변경에 영향받지 않는다. 내부 해상도 마이크로초, 저장 밀리초 |
| D-02 | 타임스탬프는 에이전트 시계를 쓴다. 서버는 세션 수립 시와 heartbeat마다 NTP식으로 시계 차이를 측정해(이동 중앙값) 기록하고, 1초 이상이면 인스턴스 상태 WARN으로 표시한다 |
| D-03 | 같은 앱·**분 경계로 정렬된** 같은 시간 범위에서 XLog 점 수, 서비스 통계 건수 합, 앱 통계 건수, 대시보드 TPS 적분은 **정확히 일치한다(오차 0)**. 범위 끝이 분 경계가 아니면 양 끝 부분 분을 원본에서 계산한다. 일치 대상은 원본 보존 기간 안이며, 그 밖은 롤업이 기준값이고 UI는 "원본 보존 기간 경과"를 표시한다. 늦은 도착으로 과거 분이 소급 변경될 수 있어 UI 자동 갱신은 최근 5분을 다시 조회한다 |
| D-04 | 요청 1건은 트랜잭션 정확히 1개다. ERROR·FORWARD·INCLUDE·ASYNC 디스패치, 비동기 하위 작업, Servlet async는 새 트랜잭션이 아니라 같은 트랜잭션의 일부다. `/error`는 서비스 이름이 될 수 없다 |
| D-05 | 분산 호출에서 호출자 HTTP step 시간은 피호출자 트랜잭션 시간보다 크거나 같다(네트워크 포함). 트레이스 뷰는 둘을 모두 보여주고 차이를 "네트워크·대기"로 표시한다 |
| D-06 | 에이전트 드롭(큐 초과), 서버 드롭(WAL 상한·쿼터), 적재 지연, 제외 요청, 늦은 도착, 시계 보정은 숨기지 않고 수집 상태 패널에 표시한다 |
| D-07 | 프로파일이 샘플링으로 없는 트랜잭션은 "프로파일 미수집(샘플링 정책)"으로, `profile_captured=1`인데 step이 없으면 "프로파일 유실(드롭)"로 구분해 표시한다 |
| D-08 | 서비스·SQL·클래스·호스트 사전 키는 64비트 내용 해시(xxh3_64)로, 같은 정규화 결과는 항상 같은 id다. 원문은 PostgreSQL 사전에 비동기로 저장한다 |
| D-09 | 메트릭은 5초 고정 주기. 누락 구간은 0이 아니라 결측으로 저장·표시한다 |
| D-10 | 에러 트랜잭션 판정 기준은 하나다: 미처리 예외 발생 또는 HTTP 5xx. 4xx는 에러가 아니며 별도 필터로 본다 |
| D-11 | `tx_id`는 전역 유일하고 시작 시각을 접두로 담는다(41비트 ms, 12비트 노드, 11비트 시퀀스. 랜덤 금지). 서버는 `tx_id`만으로 파티션·정렬 범위를 계산한다. `(app_id, tx_id)`가 겹치는 두 트랜잭션은 존재하지 않는다 |
| D-12 | SQL·외부 호출 통계는 **전 트랜잭션**에서 집계한다(프로파일 샘플링과 무관). 같은 범위에서 `Σ xlog.sql_count = Σ sql_stat.count`, `Σ xlog.ext_count = Σ ext_stat.count`가 일치한다. 프로파일은 "관련 트랜잭션" 목록에만 쓴다 |
| D-13 | 수집 경로는 중복 0·누락 0이다. 서버는 수신 배치를 WAL에 기록한 뒤 ack하고, ClickHouse insert마다 WAL 위치에서 유도한 중복 제거 토큰을 붙인다. 에이전트 재전송·서버 재시작·스풀 재적재·MV 부분 실패 재시도 어느 경우에도 원본과 롤업의 행 수가 보낸 수와 같다 |
| D-14 | 롤업은 원본의 결정적 함수다. 같은 SELECT 정의가 MV와 재구축 도구에 쓰이고, 재구축하면 바이트 단위로 같은 집계가 나온다. 서버는 매일 전날 전체에 대해 D-03·D-12 정합을 검사해 불일치 분을 기록하고 자동 재구축한다 |
| D-15 | 타임스탬프 가드: `ts > now + 5s`는 `now`로 보정, `ts < now - 7d`는 거부하고 둘 다 센다. 도착이 `ts + 60s`를 넘는 행은 저장만 하고 실시간 스트림에는 내보내지 않는다. 실시간 TPS는 도착 시각이 아니라 `ts` 버킷으로 계산한다 |
| D-16 | 메트릭 레지스트리는 이름마다 종류(gauge/counter)와 단위를 가진다. 롤업은 `sample_count`를 저장하고 gauge는 avg·max·min, counter는 first·last·리셋 보정 increase를 저장한다. `sample_count=0`은 null로 반환한다. 인스턴스당 시리즈 상한(기본 500) 초과는 드롭하고 센다 |
| D-17 | Apdex는 행에 기록된 그 시점의 T로 계산한다. T 변경은 이후 데이터부터 적용되며 원본 보존 기간 안에서 재구축으로 소급할 수 있다. UI는 범위 안의 T 변경 시점을 마커로 표시한다 |
| D-18 | 수집 중단 구간(서버 정지, 세션 끊김, 큐 초과 드롭 구간)은 XLog·TPS·메트릭 차트에 음영으로 표시하고 값 0과 구분한다 |
| D-19 | 제외 규칙에 걸린 요청은 트랜잭션을 만들지 않되 `transactions_ignored_total{reason}`로 세고, 수집 상태 패널에 "제외 N건"을 표시해 합계가 설명된다 |
| D-20 | `kind`가 HTTP가 아닌 트랜잭션(BATCH·MESSAGE)은 서비스 통계·Apdex·대시보드 TPS·p95에서 기본 제외하고 종류별로 따로 집계한다. 모든 화면의 종류 필터 기본값은 HTTP다. 컨텍스트 없이 발생한 step·SQL은 버리되 카운터로 센다 |
| D-21 | 상태 코드는 ERROR 디스패치 반영 후 최종값이다. 예외가 필터 체인을 탈출했는데 `getStatus() < 400`이면 500으로 기록한다 |
| D-22 | SQL 정규화 규칙은 고정이다: 바인드 마커(`?`, `:1`, `:name`, `$1`, `@p1`) 보존, 문자열·숫자 리터럴 → `?`, `IN (?, ?, …)` → `IN (?)`, 주석 제거, 공백 정규화, 식별자 안 숫자 보존, PL/SQL 블록·`{call}` 지원. 정규화기 버전을 사전에 기록하고 변경 시 마이그레이션한다. 실패 시 원문을 전송하지 않고 `<unparsed>`로 집계한다 |
| D-23 | 측정 불가 값(가상 스레드의 CPU·alloc, 스레드가 바뀐 비동기 구간)은 0이 아니라 결측으로 저장·표시한다 |
| D-24 | JDBC 1회 실행 = SQL step 1개. 풀 프록시·드라이버 래퍼 중첩은 집계하지 않는다 |
| D-25 | GC 메트릭은 pause와 concurrent cycle을 구분한다. "GC 시간" 알림과 `jvm_gc_pause_seconds_total`은 pause만 포함한다 |
| D-26 | 에이전트는 요청 본문·파라미터를 소비하지 않고 세션을 생성하지 않는다(`getParameter*`·`getReader`·`getSession(true)` 호출 금지, `getSession(false)`만) |

### 7.3 에이전트 오버헤드 측정 프로토콜

1. **환경.** 부하 생성기와 앱 서버는 다른 머신(또는 다른 VM, 같은 L2). 앱 서버 코어 수·메모리, CPU governor(`performance`), THP 설정, OS 이미지, JDK 빌드를 기록한다. 설정 파일 해시를 보고서에 적는다.
2. **JVM 고정.** `-Xms2g -Xmx2g -XX:+UseG1GC -XX:+AlwaysPreTouch -Xlog:gc:file=gc.log`. on/off 동일.
3. **워크로드.** 고정 도착률(open model, k6 `constant-arrival-rate`) 1,000 TPS. 믹스: DB 1~3 SQL 60%, 외부 HTTP 1회 20%, N+1(SQL 20개) 10%, 느린 요청(300ms) 5%, 에러 5%. 트랜잭션당 평균 step 약 8. 프로파일 정책은 기본값과 최악(정상 100%) 둘 다.
4. **절차.** 워밍업 3분 제외, 측정 10분, on/off 교대 3회씩(A-B-A-B-A-B) 같은 날. off 3회 CPU 변동계수가 2%를 넘으면 무효.
5. **CPU.** 앱 프로세스 `/proc/<pid>/stat` utime+stime(또는 cgroup `cpu.stat usage_usec`) 차분. 에이전트 스레드 CPU는 `ArgosThread` 합산을 자가 진단으로 보고하고 병기.
6. **지연.** 부하기 측 HDR 히스토그램 p50·p95·p99·p99.9와 95% 신뢰구간. 차이가 신뢰구간 안이면 "차이 없음".
7. **메모리.** 10분 부하 후 `jcmd GC.run` 2회 → `GC.class_histogram`에서 `argos.` 인스턴스 합 ≤ 64MB. 메타스페이스 차 ≤ 32MB, NMT `Internal+Other` 차 ≤ 16MB, 스레드 수 차 ≤ 6. 72시간은 1시간 간격 히스토그램 선형회귀 기울기 ≤ 0.
8. **기동.** JVM 시작 → Spring `Started … in` 로그 + 포트 바인딩 시각. 10회 중앙값. 기본 샘플 앱과 heavy 샘플 앱(의존성 200 jar 이상, 클래스 3만 개 이상) 둘 다.
9. **컨테이너.** `docker run --cpus=2 --memory=4g`(cgroup v2)에서 반복 → N-29.
10. **가상 스레드.** Boot 3.2+ 앱은 `spring.threads.virtual.enabled=true`로 반복 → N-28.
11. **보고.** `docs/bench/<날짜>-<커밋>.md`에 환경, 원시 수치, 통계, 그래프, 재현 명령. 수치 없는 "충족"은 무효. 가능하면 같은 하드웨어에서 OpenTelemetry Java Agent를 함께 측정해 참조점으로 병기.

## 9. 제품 완성도 요소

기능이 아니지만 "설치해도 문제없이 돌아가는 완성도"를 만드는 것들이다. 03 문서 Gate 2의 근거다.

### 9.1 패키징·설치

- 단일 노드: `tar.gz` + 설치 스크립트(systemd) 및 Docker Compose. 둘 다 공식 지원. 컨테이너 이미지는 linux/amd64·arm64.
- **데모 프로파일**: `docker compose --profile demo up` 한 번으로 서버·ClickHouse·PostgreSQL·샘플 앱(에이전트 부착)·부하 생성기가 뜨고 60초 안에 XLog 점이 흐른다. 데모 트래픽에 느린 요청·에러·N+1·분산 호출을 포함해 S-01·S-03·S-05를 바로 볼 수 있다. 데모 모드 배너 표시.
- 쿠버네티스: Helm 차트(1.x).
- 에이전트: `argos-agent.jar` 1개 + `argos-agent.yml`. `-javaagent` 한 줄. 서버 주소·앱 이름·환경·토큰만으로 동작. `--check` 사전 점검. 설치 스니펫(`-javaagent`, Dockerfile, `bootRun`, Tomcat `setenv.sh`).
- 설치 시 자격증명(ClickHouse·PostgreSQL·마스터 키·초기 관리자)을 랜덤 생성해 `.env`(0600)에 쓴다. 기본 비밀번호 없음. DB 포트는 호스트에 노출하지 않는다. 노출 포트는 UI/API(8080, 리버스 프록시 443 가이드)와 gRPC(9100)뿐.
- 최초 접속 설치 마법사: 1회용 설정 토큰(서버 로그·`conf/setup-token`) 입력 후 관리자 생성, IP 수집 모드 선택(강제), 첫 앱 등록과 에이전트 설치 안내. 무인 설치는 `ARGOS_ADMIN_PASSWORD_FILE`.
- 에어갭: 전체 오프라인 번들(컨테이너 이미지, 체크섬, GPG 서명, 공개키 지문 포함).

### 9.2 업그레이드·운영

- 서버: 스키마 마이그레이션 자동(PostgreSQL은 Flyway, ClickHouse는 자체 러너·이력은 PostgreSQL `ch_schema_history`). 전진 전용, 지원 중인 모든 이전 마이너에서 현재로. 롤백은 직전 마이너. MV 교체 4단계. 업그레이드 가이드는 마이너마다.
- 호환: 서버 `X.Y`는 에이전트 `X.(Y-2)`~`X.Y`를 수용. 에이전트가 서버보다 새 버전이면 거부하고 이유를 세션 응답과 관리 화면에 표시. 관리 화면이 구버전·호환 불가를 경고.
- 보존 변경: 설정 파일 → 기동 시 러너 적용 → 감사 로그. 연장은 `MODIFY TTL`(재물질화 없음), 단축은 `DROP PARTITION`.
- 디스크: 80% 경고, 90% 비상 보존 단축(오래된 profile_step → xlog 순 DROP, 표시·알림), 95% WAL만 쓰고 초과는 서버 드롭으로 카운트.
- 백업: PostgreSQL `pg_dump` 일 1회 **필수**(RPO 24h, 7일 보관). ClickHouse는 기본 "재구축 가능한 텔레메트리, 백업 선택", 켜면 외부 대상(NAS·S3 호환)으로 증분. 같은 디스크에 백업하지 않는다. 백업 산출물 0600·암호화 옵션. 복구 리허설 문서(마스터 키 복구 포함).
- 자기 모니터링: 수신량, 큐, 적재 지연, 드롭, 디스크, parts, 인증서·토큰 만료를 서버 자신이 기록하고 기본 규칙으로 알림. Prometheus 노출(F-S20).
- 진단 번들: 서버·에이전트 로그(토큰·비밀값 마스킹), 설정, 버전, 시스템 정보를 한 번에 모으는 스크립트.
- 인스턴스 정리: N일(기본 7) 미접속 인스턴스 자동 보관, 30일 후 정리(설정).

### 9.3 보안·개인정보

보안 요구는 기능과 같은 무게로 다루며, 모든 항목은 06 문서의 SEC-xx 요구로 측정·검증한다. 목표 수준은 **OWASP ASVS 4.0 Level 2**다.

- **에이전트 인증·전송**: 앱 단위 토큰(서버는 해시만 보관, 1회 표시, 만료·회전·즉시 폐기), TLS 1.2+ AEAD 암호군, 호스트명 검증 필수, 자체 CA 운영 가이드, 인증서 만료 알림. 평문·검증 생략은 명시 플래그와 경고가 함께 있을 때만. (SEC-01~10)
- **원격 명령·동적 설정**: 환경 덤프는 에이전트에서 비밀값 마스킹 후 전송하고 관리자 전용. 원격으로 바꿀 수 있는 설정은 에이전트 로컬 설정이 허용한 키로 한정하며, 바인드 파라미터·헤더·사용자 식별자·쿼리스트링 수집과 커스텀 메서드 추가는 원격 활성화 기본 불허. 명령은 TTL·동시 실행 상한·감사 로그. (SEC-20~26)
- **수집 데이터의 개인정보**: 02 문서의 데이터 분류표가 필드별 기본 수집 여부·마스킹·보존·삭제 경로를 정한다. 기본값은 "수집 안 함 또는 마스킹"이다: SQL 바인드 파라미터 마스킹, URL 쿼리스트링 제거, 사용자 식별자 미수집, HTTP 헤더 화이트리스트, 예외 메시지 정규식 마스킹, 정규화 실패 SQL 원문 미전송. 원격 IP는 설치 시 모드(원문·마스킹·미수집)를 선택한다. 사용자 식별자·IP 기준 삭제 API를 제공한다. (SEC-30~3A)
- **서버·UI**: httpOnly 쿠키 세션(액세스 15분, 리프레시 회전, 서버 측 즉시 무효화), CSRF 토큰, WebSocket 핸드셰이크 인증·Origin 검사, 1회용 설정 토큰으로 보호되는 초기 관리자 생성, 비밀번호 정책(12자·금지 목록·bcrypt cost 12·10회 실패 잠금), 역할 3종의 권한 매트릭스(민감 작업은 관리자 전용), 보안 헤더·CSP 값 명시, Actuator 접근 제한, API 레이트 리밋. (SEC-40~56)
- **알림 채널**: 웹훅 목적지 검증(사설·루프백·메타데이터 대역 차단, 리다이렉트 미추종), 채널 비밀값 마스터 키 암호화, 웹훅 서명, SMTP STARTTLS. 알림 본문에 수집 원문(SQL·파라미터·user_id·IP·예외 메시지)을 넣지 않는다. (SEC-39, 51~54)
- **UI 렌더링**: 수집 데이터 전부를 신뢰할 수 없는 입력으로 다룬다. HTML 문자열 조립 금지 린트, XSS 시드 데이터 E2E, CSV 수식 주입 방지. (SEC-60~64)
- **공급망·배포**: 셰이딩 전 의존성 기준 SBOM(CycloneDX) 생성·동봉, SBOM 기반 CVE 스캔 Critical·High 0(예외는 문서·승인), 릴리스 자산 체크섬·서명(폐쇄망 검증용 GPG 병행), 재현 가능 빌드, 비밀 스캔, 설치 시 랜덤 자격증명, DB 포트 비노출. (SEC-70~77)
- **감사 로그**: 인증·권한·토큰·명령·설정 변경에 더해 민감 데이터 열람과 내보내기를 기록한다. API로 수정·삭제 불가, 기본 보존 1년, syslog 출력 옵션. (SEC-80~84)
- **프로세스**: `SECURITY.md`(취약점 접수·조정 공개 90일·지원 버전), 위협 모델 문서, ASVS L2 체크리스트, 보안 테스트 스위트, 릴리스 전 인증 상태 ZAP 활성 스캔. (SEC-90~93)
- 프로젝트 라이선스는 Apache-2.0. 배포물의 의존성은 Apache-2.0 호환 허용 목록으로 제한하고 CI가 검사한다. `NOTICE`·서드파티 고지·버전 매니페스트를 빌드가 생성하며 셰이딩된 에이전트 jar에도 포함한다(10장).

### 9.4 문서

사용자 문서는 **영어 원본 + 한국어 번역**(릴리스 후 2주 내)이다: README(스크린샷 3장), 빠른 시작, 설치(Compose·tar·에어갭), 에이전트 설정 레퍼런스, 서버 설정 레퍼런스, 호환성 표(검증·미검증·커뮤니티 검증 구분), 업그레이드 가이드(마이너마다), 호환성 약속, 운영 매뉴얼(백업·복구·용량·보존), 트러블슈팅(증상 → 원인 → 조치), 수집 데이터 명세(`docs/data-collected.md`), CHANGELOG, SECURITY, CONTRIBUTING, GOVERNANCE, ADR. 기획·설계 문서(01~06, 10번대)는 한국어 원본으로 두고 영문 1페이지 요약을 둔다. 문서는 코드와 같은 저장소에서 같은 PR로 갱신한다.

### 9.5 에이전트 도입·변경 절차 (제품이 지원해야 하는 흐름)

변경 통제가 있는 운영 조직의 흐름(변경 요청 → 승인 → 점검 시간 → 적용 → 검증 → 롤백 대비)에 제품 기능이 각각 대응한다.

1. **사전 점검**: `java -jar argos-agent.jar --check --config argos-agent.yml`로 서버 연결·TLS·토큰·시계 차이·JDK·감지된 WAS/Spring 호환성 판정을 표로 출력한다(종료 코드 0/1). 변경 요청서에 첨부한다.
2. **사전 등록**: 관리자가 앱(이름, 환경)을 등록하고 토큰(만료일)을 발급한다. 자동 등록은 환경별 서버 설정으로 허용한다(F-S30).
3. **카나리**: 인스턴스 1대에 적용 → 인스턴스 비교 표에서 미적용 인스턴스와 CPU·p99·힙 비교(N-01·N-03) → 자가 진단에서 드롭 0·모듈 자동 비활성 0 → 24시간 뒤 확대.
4. **롤백 경로 두 가지**: 즉시(킬 스위치, 재기동 없음, 10초 이내, N-25) / 완전(`-javaagent` 제거 후 재기동). 둘 다 설치 가이드에 명시한다.
5. **설정 변경**: 관리 화면에서 사유 입력 → diff 확인 → 적용 → 인스턴스별 결과(거부 키 포함) → 감사 로그. 되돌리기는 한 번의 동작(F-S29). 원격 변경 불가 키는 앱 소유자가 로컬 yml에서만 바꾼다(SEC-23).
6. **업그레이드**: 서버를 먼저 올린다. 에이전트는 호환 범위 안에서 앱 재기동 일정에 맞춰 순차 교체한다. 관리 화면이 구버전·호환 불가를 경고한다.
7. **토큰 회전**: 새 토큰 발급 → 에이전트 설정 교체(재기동 또는 리로드) → 유예 기간(기본 7일) 뒤 구 토큰 폐기. 유예 중 구 토큰 사용 인스턴스를 목록에 표시한다.
8. **감사**: 위 모든 동작은 누가·언제·무엇을·왜·결과를 감사 로그에 남긴다(F-S08).

## 10. 오픈소스 프로젝트 요소

Argos는 Apache-2.0 오픈소스로 모두에게 무료로 공개한다. 9장이 "설치해도 문제없이 돌아가는 완성도"라면, 이 장은 **"모르는 사람이 받아서 믿고 쓰고 고칠 수 있는 완성도"**다. 기능이 아니지만 1.0의 요구이며, 각 항목은 O-xx 식별자를 가지고 03 문서 Gate 0·1·1.5·2의 근거가 된다.

## 11. 로드맵

일정은 사람의 검수 속도가 병목이므로 달력보다 **게이트**로 관리한다. 괄호의 기간은 참고용 추정이다. 저장소 공개 시점은 미결 15(추천: WO-00부터 공개하되 Gate 1 전에는 릴리스·홍보를 하지 않고 README에 "pre-release, 지원 없음"을 명시).

### Phase D: 설계 (지금)

- 02 아키텍처를 개정하고 10번대 설계 문서(에이전트, 프로토콜, 서버, 저장소, API, UI, 보안, 배포·운영, 테스트, 저장소·빌드·릴리스)를 작성한다.
- 설계 완료 후 04 작업 지시서를 설계 기반으로 재작성한다.

### Phase 0: PoC (2~3주)

목표: 기술 리스크를 숫자로 닫고, 오픈소스 골격을 첫 커밋에 넣는다.

- 에이전트 PoC: 셰이딩·단일 jar bootstrap·격리 클래스로더·JPMS read edge 구조, Servlet·Spring MVC·JDBC 계측, JDK 8/17/21 기동, 오버헤드 측정(7.3 프로토콜), 전송 스택 비교.

- UI PoC: XLog 캔버스 10만 점 렌더와 드래그 선택.
- 오픈소스 골격: LICENSE·NOTICE·SPDX·DCO·라이선스 허용 목록 검사, GitHub 조직, 식별자 세트(미결 12~15).

| 메인테이너 | 사람 | 이슈 트리아지, 외부 PR 리뷰·머지, 릴리스 태그, 보안 신고 대응, 거버넌스 문서 유지 |
| 구현 | Claude Code | 04 문서의 작업 지시서 단위로 구현, 테스트, 문서 갱신, 완료 보고. 외부 PR 1차 리뷰 보조(최종 승인은 사람) |
| 검수 | 사람 | 03 문서 기준으로 수락 테스트, 반려·재지시, 핵심 경로 코드 리뷰 |
| 테스트 환경 | 사람(사내 서버) | 호환성 매트릭스·부하·실환경 운영 환경 제공, 신뢰 브랜치 전용 CI 러너 |
| 외부 기여자 | 커뮤니티 | 이슈·PR·호환성 보고. CONTRIBUTING과 DoD를 따른다 |

작업 흐름

1. 사람이 04 문서에서 작업 지시서(WO) 하나를 골라 Claude Code에 전달한다.
2. Claude Code가 구현 + 자동 테스트 + 문서 갱신 후 03 문서 템플릿으로 완료 보고한다.
3. CI가 자동 게이트(빌드, 테스트, 정적 분석, 보안 검사, 매트릭스)를 돌린다.
4. 사람이 수락 시나리오를 수행하고 통과 또는 반려한다. 반려 사유는 WO에 기록한다.
5. DONE이 되면 다음 WO로. 아키텍처 결정을 바꿔야 하는 발견은 02·설계 문서를 먼저 고치고 ADR을 남긴다.

원칙

- 지시서 하나는 하루~며칠 분량. 크면 쪼갠다.
- "테스트 없는 완료"는 없다. 테스트가 수락 기준을 직접 검증해야 한다.
- 사람의 검수 시간이 병목이다. 수락 시나리오는 15분 안에 끝나도록 설계한다.
- 사내 시스템 운영 기록은 비공개 저장소에 두고, 공개 저장소에는 익명화 요약(`docs/field-reports/`)만 둔다.
