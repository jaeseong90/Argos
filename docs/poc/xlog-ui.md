## 1. 확인할 것

15 §7의 Canvas 2D 구조가 10만 점에서 16ms/프레임(N-14)을 지키는가, 드래그 선택·요약이 자연스러운가. 15 §18의 미결 두 가지에 데이터로 답한다.

- §18 #2: 색별 3패스 `rect` 누적 + `fill` 1회가 10만 점에서 16ms 이내인가. 미달이면 `ImageData` 픽셀 플롯으로 바꾼다.
- 오프스크린 점 레이어(§7.2): 점 레이어를 데이터·범위·크기가 바뀔 때만 다시 그리고 호버·선택은 overlay만 그리는 구조가 효과가 있는가. 실시간에서 `drawImage` 시프트 + 새 점만 그리기(§7.5)가 효과가 있는가.

## 3. 측정 방법

### 3.1 무엇을 프레임 시간으로 보는가

Canvas 2D 호출의 JavaScript 시간은 실제 비용이 아니다. Chrome은 캔버스 명령을 기록만 하고, 래스터는 GPU 프로세스(`CrGpuMain`)에서 나중에 한다. 이번 측정에서 `path` 10만 점은 JS 시간이 p50 11~12ms였지만 실제 프레임 시간은 62~91ms였다(4장). 15 §15의 "`performance.now` 루프 60프레임 평균"을 JS 시간으로 재면 미달을 통과로 잘못 판정한다.

그래서 `ui/perf/xlog-frame.spec.ts`는 Chrome tracing(CDP `Tracing.start`, DevTools Performance 패널과 같은 카테고리)으로 모든 프로세스의 작업을 기록하고, 프레임마다 다음을 계산한다(`ui/perf/lib/frames.ts`).

- 프레임 경계: 페이지가 `perf=1`일 때 그리는 프레임마다 남기는 user timing `xlog:frame`(그리기 JS의 시작·끝). 프레임 i의 창은 [시작 i, 시작 i+1)이다.
- 창 안에서 렌더링 파이프라인 스레드별 바쁜 시간(최상위 `RunTask` 합, 중첩은 합집합): 렌더러 메인(`CrRendererMain`), 렌더러 컴포지터(`Compositor`), GPU 메인(`CrGpuMain`, GPU를 브라우저 프로세스 안에서 돌리면 `Chrome_InProcGpuThread`), 디스플레이 컴포지터(`VizCompositorThread`), 있으면 `DrDcThread`. vsync를 기다리기만 하는 `GpuVSyncThread`와 스레드 풀은 넣지 않는다.
- **프레임 시간 = 그 창에서 가장 바쁜 스레드의 바쁜 시간.** 단계는 서로 다른 프레임을 병렬로 처리하므로(메인이 i+1을 기록하는 동안 GPU가 i를 래스터) 가장 느린 단계가 프레임률을 정한다. 이 값이 16ms 이하면 모든 단계가 초당 60프레임을 따라간다. rAF 간격과 달리 디스플레이 주사율 단위로 올림되지 않고(60Hz 화면에서 간격은 아무리 빨라도 16.7ms), JS 시간과 달리 GPU 래스터를 포함한다.

함께 기록하는 값: 프레임 간격(trace 기준), 프레임 JS 시간(`xlog:frame` 길이), 스레드별 p95 바쁜 시간, 가장 바쁜 스레드의 비율, 같은 작업을 tracing 없이 돌린 페이지 자체 측정(`window.__xlogPerf`의 rAF 간격·JS 시간). tracing 없는 rAF 간격은 trace 지표의 독립 검증이다. 정적 시나리오에서 두 값은 같은 크기로 나왔다(4.4).

### 3.2 판정 통계

01 N-14·15 §14는 "16ms/프레임 이하"만 정하고, 15 §15는 "60프레임 평균 ≤ 16ms"를 정한다. 판정 통계는 **ADR-0003 C-34로 확정되었다: p95와 평균이 16ms 이하면 통과, max는 보고만 한다.** 하네스는 **p95 ≤ 16ms**와 15 §15의 **평균 ≤ 16ms**를 함께 요구한다(`ui/perf/lib/stats.ts`의 `checkFrameBudget`). 최대값은 보고만 한다. 공유 머신에서는 GC나 다른 프로세스 한 번이 한 프레임을 늘릴 수 있기 때문이다. 프레임이 60개 미만이면 실패로 본다. 판정 단위는 **ADR-0003 C-35로 런마다다**. 3회 런 각각의 p95와 평균이 16ms 이하여야 통과이고, 3회를 합친 분포는 보고용이다. 하네스의 자동 판정(Playwright 통과·실패, `checkFrameBudget`)은 아직 시나리오의 모든 런을 합친 분포로 한다. 그래서 C-35 판정은 결과 요약표의 `Max run p95`·`Max run mean` 열로 읽는다. 두 열은 런 하나의 p95·평균 중 가장 큰 값이고, 둘 다 16ms 이하면 모든 런이 통과다. 1~3차 요약 md에는 이 열이 없어 런 표의 런별 값으로 본다.

측정 전제가 깨진 런은 수치와 관계없이 판정 시나리오를 실패시킨다(`ui/perf/lib/frames.ts`의 `measurementProblems`). trace에 렌더러 메인 스레드나 GPU 스레드(`CrGpuMain`, GPU를 브라우저 프로세스 안에서 돌리면 `Chrome_InProcGpuThread`)가 없거나, Chrome이 trace 데이터 유실을 알린 경우다. GPU 스레드가 빠지면 프레임 시간이 메인 스레드만 반영해 `path` 10만 점(JS 약 12ms)이 통과로 오판되기 때문이다. 비교 시나리오는 이를 메모로만 남긴다.

리뷰 r1부터 모든 시나리오를 DPR 1과 2에서 각각 잰다(`XLOG_PERF_DPR`, C-34). 제목에 `dpr=<n>`이 붙고 결과 표에 DPR과 캔버스 백킹 크기(점 레이어 / overlay)가 남는다.

모든 시나리오는 워밍업(정적 30프레임, 실시간 3초, 호버 1회) 뒤 3회 측정한다. 런마다 직전에 머신 전체 CPU 부하를 2초 표본으로 재고(`os.cpus()` 기준, Windows `typeperf "\Processor(_Total)\% Processor Time"`과 같은 값), `XLOG_PERF_MAX_LOAD`(기본 20%) 이하가 될 때까지 최대 `XLOG_PERF_MAX_WAIT`(기본 60)초 기다린다. 기다려도 내려가지 않으면 측정하고 그 런을 "조용하지 않음"으로 표시한다. 런 중 부하(측정 대상 브라우저 포함)도 기록한다. 이 문서에서 "조용한 런"은 이 하네스 정의(런 직전 부하 ≤ `XLOG_PERF_MAX_LOAD`, 기본 20%)만 뜻한다. 런 중 부하는 측정 대상 브라우저를 포함하므로 조용함 판정에 쓰지 않고 따로 적는다.

브라우저 조건: Playwright 1.64.1의 Chromium 156.0.8078.4(Chrome for Testing), new headless(`channel: 'chromium'`), 뷰포트 1366×768, 플롯 1256×384 CSS px(1·2차. 좌표 수정 후 3차부터 1254×382, 4.6). DPR은 1~3차가 1뿐이고, 4차(리뷰 r1 반영 후, 4.7)는 1과 2(Playwright `deviceScaleFactor`)다. DPR 2에서 overlay는 2668×840, 점 레이어는 1254×382 × 상한 배율이다.

WO-33이 이 시간을 직접 재고, 목록 가상화(WO-30 DataTable)·서버 검색 목록(15 §7.4)과 함께 판정한다.
- "드래그 선택·요약이 자연스러운가"(WO-04 목표): 캔버스 쪽은 자연스럽다. 드래그 중 프레임은 런별 p95 2.7~3.9ms이고 선택 계산은 대개 약 1ms다. 놓는 순간은 한 번 멈칫한다. 요약 + 목록 1,000행 커밋이 한 태스크로 47~104ms 걸리고 그 프레임이 140~313ms가 된다(4.7.3). C-36에 따라 이 항목은 WO-33 수락 기준(화면 반영 p95 ≤ 100ms)으로 판정한다. 이 PoC에서는 그 예산을 넘을 수 있는 참고 항목으로 기록한다.

## 5. 15 §18 미결에 대한 답

### 5.1 §18 #2: 색별 3패스 `rect` 누적 fill이 10만 점에서 16ms 이내인가

**아니다.** 10만 점 전체 재그리기의 프레임 시간이 p50 62~91ms, p95 79~145ms다(1~3차 합산, 4.2, 3차는 4.6). 5만 점도 p95 33~74ms로 미달이고, 1만 점(p95 7.0~8.0ms)만 통과한다. 15 §7.2가 예상한 8ms는 메인 스레드 JS 시간(10만 점 p50 11~12ms)에 가깝지만, 실제 비용은 GPU 프로세스(`CrGpuMain`)가 10만 개 사각형 패스를 래스터하는 시간이다. 프레임의 99%에서 GPU 스레드가 가장 바빴다. 점마다 `fillRect`(`rect` 방식)는 더 느리다(10만 점 p95 125ms).

**`ImageData` 픽셀 플롯은 기준 안이다.** 최적화 전 루프(1~3차)는 3회 합산으로는 통과였지만 C-35의 런 단위로는 1·2차가 미달이었다(아래). 리뷰 r1 최적화 뒤의 판정 런(4.7.3)은 런 단위로 12건 모두 통과다(런별 p95 최대 9.8ms). 이하 이 단락은 최적화 전 값이다. 10만 점 p50 10.2~10.4 / p95 14.4~15.5 / max 17.7~18.4ms, 평균 10.8~11.0ms다(1차·2차). 3차(모든 런 조용함)는 p50 9.7 / p95 10.9 / max 15.7ms다. 런 단위로 보면 런별 p95가 1차 12.5~16.7ms, 2차 10.5~16.6ms, 3차 10.3~11.3ms이고, 조용한 런인 1차 런 1(16.7ms)과 2차 런 1(16.6ms)이 런 단위 p95 16ms를 넘었다(4.3). 5만 점 p95 7.0~10.9ms, 1만 점 p95 2.9~6.4ms다. GPU 작업이 텍스처 업로드 하나로 줄고 비용이 메인 스레드의 픽셀 쓰기로 옮겨 간다. `path`는 2차(런 중 부하 56~60%)에서 10만 점 p50이 1차보다 47% 늘어 경합에 민감했다. `pixels` 10만 점은 1차·2차가 거의 같았지만 2차 런 중 부하가 20~35%로 낮아서, 같은 부하에서의 비교는 아니다. 다만 10만 점의 여유는 작다. 1·2차 합산 p95의 여유가 0.5~1.6ms뿐이고, 런 단위로는 1·2차에서 런 하나씩이 16ms를 0.6~0.7ms 넘었다(3차는 런별 p95 최대 11.3ms로 여유 4.7ms). 최적화 전 루프라면 15 §18 #2가 기준으로 둔 저사양 노트북에서는 넘을 가능성이 높았다(이 머신은 2021년 중급 노트북 CPU다). 최적화 뒤 여유는 4.7.3을 본다.

결정과 반영(ADR-0003 C-34로 결정됨):

1. 기본 그리기 방식은 `pixels`다. 리뷰 r1에서 렌더러(`XLogCanvas`의 `drawMode`)와 데모(`/xlog-poc`의 `render`) 기본값을 `pixels`로 바꿨다. `path`(15 §7.2 원안)·`rect`는 비교·진단용으로 남긴다. 15 §7.2 "그리기" 행의 갱신은 문서 담당이다(이 WO는 15 문서를 고치지 않는다).
2. 리뷰 r1에서 점 쓰기 루프를 최적화했다(점별 y 캐시로 매 프레임 `log10` 제거, 2×2 점 직접 대입). 전후 비교와 최악 구성(y=로그 + 색 기준=서비스)·DPR 2 결과는 4.7에 있다. 남은 후보: 바뀐 영역만 다시 쓰기(범위 변경도 시프트 + 부분 그리기), 10만 점 초과 시 서버 샘플링 상한 낮추기. `OffscreenCanvas` 워커는 15 §18 #8(미사용 가정)과 충돌하므로 별도 결정이 필요하다.

### 5.2 오프스크린 점 레이어(2겹 캔버스)와 실시간 증분 그리기는 효과가 있는가

**있다.** 이 구조 없이 `path`는 실시간·상호작용 모두 기준을 넘고, `pixels`는 실시간 전체 재그리기만 넘는다. `pixels`의 상호작용은 매 프레임 재그리기 시 10~16ms로 경계다.

- 호버·드래그: 런마다 173프레임 동안 점 레이어 재그리기 0회, 조용한 런의 프레임 p95 2.6~4.9ms(메인 스레드 overlay 그리기와 히트 테스트)다. 같은 10만 점을 매 프레임 다시 그렸다면 `path` 62~130ms, `pixels` 10~16ms가 든다.
- 실시간(10만 점 + 초당 500점): 증분 그리기(`drawImage` 시프트 + 새 점만)는 시나리오 합산 p95 3.2~3.9ms다(2차 `pixels`는 런 중 부하 97%였던 런 1과 조용하지 않은 런 2 때문에 7.9ms). 조용한 런의 런별 p95는 3.0~4.6ms다. 예외는 직전 16%로 조용하지만 런 중 부하가 97%였던 2차 `pixels` 런 1(11.8ms)이다(4.5). 같은 조건에서 묶음마다 전체 재그리기(`incremental=0`)는 `path` p95 91~178ms, `pixels` p95 18.7~20.2ms로 둘 다 미달이다. 증분 그리기는 방식과 상관없이 필요하다.
- 리뷰 r1 수정(창 오른쪽 밖 점 누락): 증분 프레임은 점 레이어를 장치 픽셀 단위로만 민다. 그래서 그려진 창의 끝이 범위 끝보다 1px 미만 앞설 수 있다. 수정 전에는 그 사이에 들어온 새 점과 일시정지 중 창 밖에 쌓인 점을 "그렸다"고 처리해, 다음 전체 재그리기 전까지 그리지 않았다. 리뷰어 측정은 정상 상태 7~16% 누락, 일시정지 20초 → 재개 뒤 약 20초 폭의 빈 띠였다. 지금은 창 끝 뒤라서 건너뛴 점을 "대기"로 남긴다(버퍼 꼬리 기준 개수라 머리 쪽 evict와 무관). 다음 프레임부터 창이 그 점에 닿으면 그린다. 이미 레이어에 있는 점은 다시 그리지 않는다. 전체 재그리기도 범위 끝 뒤의 점을 대기로 남긴다. 일시정지 중에는 대기 점을 프레임마다 다시 검사만 한다(그리기 없음, 1패스 순회). 재개 시 시프트가 레이어 폭보다 작으면 증분 1프레임으로 따라잡고, 크면 전체 재그리기다. 세 방식(`pixels`·`path`·`rect`) 모두 같은 경로다. 단위 테스트(`renderer.test.ts` "PointLayer realtime")가 1254px·300초 창·1초 이동·초당 500점 60초, 묶음 추가 직후 창 이동 전 프레임, 일시정지 20초 → 재개(중간 전체 재그리기 포함)에서 창 안의 점이 하나도 빠지지 않음을 레이어 래스터로 확인한다. 수정 전 동작으로 되돌리면 이 9건(3 시나리오 × 3 방식)이 모두 실패한다. 창 폭(300초)보다 긴 일시정지 뒤 재개가 전체 재그리기로 모든 점을 그리는 것도 같은 테스트 묶음에서 고정한다.

E2E 공통 픽스처·오라클·서버 설정은 18 §13대로 `ui/e2e/fixtures/`에 둔다(리뷰 r1에서 `ui/e2e/support/`에서 옮겼다). 테스트 이름은 18 §3대로 ID를 앞에 붙인다(`T-E2E-xlog-<n> …`, Vitest는 `T-UI-001 …`). 모든 테스트에 공통 훅(`ui/e2e/fixtures/fixtures.ts`, 15 §15 전역 훅)이 붙는다. 테스트 후 `window.__xss` 미정의, dialog·페이지 오류·콘솔 error·CSP 위반 0, 다른 출처 요청 0을 단언한다. 콘솔 error의 예외는 픽스처 옵션 `ignoredConsoleErrors`(기본 없음)에 지정한 패턴과 맞는 메시지뿐이다. 이 옵션은 양성 대조 전용이고, 예외로 둔 메시지는 테스트의 `ignored-console-error` 주석으로 남는다. `xlog-poc.spec.ts`는 데이터에서 만들어진 `img`·`svg`·`iframe`·`script`·`object`·`embed` 요소가 0개인지도 본다.

CSP 위반 0은 정책이 있을 때만 의미가 있다. 그래서 스위트가 직접 띄우는 `vite preview`는 `ui/vite.config.ts`의 `preview.headers`로 16 §9.9(SEC-46)의 CSP에서 nonce와 report만 뺀 정책(`default-src 'self'; script-src 'self'; style-src 'self'; img-src 'self' data: blob:; font-src 'self'; connect-src 'self'; worker-src 'self' blob:; object-src 'none'; base-uri 'self'; form-action 'self'; frame-ancestors 'none'`)을 보낸다. nonce는 서버가 요청마다 `index.html`에 넣는 방식이라 정적 preview로는 만들 수 없고, WO-30(DSN-15-09)에서 검증한다. dev 서버에는 넣지 않는다(React refresh의 인라인 프리앰블이 막힌다). 훅은 메인 프레임 문서 응답마다 `Content-Security-Policy` 헤더가 있는지도 단언한다. `ARGOS_UI_BASE_URL`로 외부 서버를 대상으로 하면 헤더를 요구하지 않고 테스트에 `csp-not-verified` 주석을 남긴다. 이때 CSP 위반 0은 그 서버가 보내는 정책 아래에서만 센다.

훅이 실제로 실패할 수 있는지는 `ui/e2e/specs/global-hooks.spec.ts`가 양성 대조 5건으로 확인한다. 페이지에 인라인 스크립트를 넣으면 preview CSP가 막고 위반 1건(`script-src-elem`)이 기록되어야 한다.

- 단위 수준 1: 훅 검사 함수를 직접 부르면 "CSP violations"로 실패해야 한다.
- 단위 수준 2(특이성): Chrome은 막은 스크립트를 콘솔 error("Executing inline script violates the following Content Security Policy directive 'script-src 'self''. …")로도 남긴다. 그래서 대조는 이 메시지 하나만 `ignoredConsoleErrors`로 예외로 둔다. 이 테스트는 그 콘솔 error가 실제로 나오고 패턴과 맞는지 확인한다. 이어서 위반이 기록된 동안은 검사가 "CSP violations"로 실패하고, 기록된 위반만 비우면 검사 전체가 통과함을 단언한다. 즉 이 대조를 실패시키는 것은 CSP 위반 검사 하나뿐이다.
- 단위 수준 3: 같은 옵션을 줘도 패턴과 맞지 않는 콘솔 error는 그대로 실패해야 한다(옵션이 다른 오류를 삼키지 않음).
- 단위 수준 4: 문서 응답에서 CSP 헤더를 지우면 헤더 검사가 실패해야 한다.
- 픽스처 경유: `test.use({ ignoredConsoleErrors: [CSP 콘솔 메시지] })`로 같은 주입을 하고, 픽스처의 사후 검사 때문에 기대 실패(`test.fail()`)로 끝나야 한다. 콘솔 메시지가 예외라서, 픽스처가 CSP 위반 검사를 빠뜨리면 이 테스트는 통과해 버린다. Playwright는 기대 실패 테스트의 통과를 실패로 보고한다. 리뷰 r1 검증의 지적 r1-new-2를 반영하기 전에는 이 예외가 없었다. 그래서 CSP 검사를 지워도 콘솔 error 검사 때문에 기대 실패가 유지되어, 픽스처 수준의 검출은 단위 수준 1에만 기대고 있었다. 변이 확인 결과는 6.2에 있다.

이 다섯 테스트는 `ARGOS_UI_BASE_URL`을 쓰면 건너뛴다.

원인: `ui/src/xlog/engine.ts`의 `plotPoint()`가 포인터 좌표를 컨테이너의 `getBoundingClientRect()`(테두리 포함 border box) 기준으로 계산한다. 그런데 캔버스는 컨테이너의 padding box(1px 테두리 안쪽)에 놓인다. 그래서 호버와 드래그 좌표가 x·y 모두 1px 어긋난다. 플롯 위 끝에서 시작한 드래그가 축 상한 위의 점(위 끝에 그려짐)을 놓치고, 시간 경계가 1px(약 1.4초) 밀린다. 같은 이유로 `measure()`도 border box 크기로 overlay 캔버스의 픽셀 크기를 잡아, CSS 크기(padding box)보다 가로·세로 2px 크다. 그래서 overlay(축·선택 사각형·호버 표시)가 약 0.15% 늘어나 그려진다.

수정(통합 단계에서 반영): 두 곳 모두 overlay 캔버스의 `getBoundingClientRect()`(padding box를 채운다)를 쓴다. 그 결과 쓰이지 않게 된 `container` 필드는 지웠다(`tsc`의 `noUnusedLocals`). Vitest의 `mockLayout`은 모든 요소에 같은 사각형을 돌려줘서 이 결함을 잡지 못했다. 그래서 `ui/src/xlog/engine.test.ts`에 회귀 테스트("measures and maps pointers in the padding box, not the bordered container box")를 더했다. 컨테이너에는 1px 테두리를 포함한 border box를, overlay에는 padding box를 따로 주고, 플롯·overlay 크기와 플롯 (0, 0)에서 시작한 드래그의 데이터 경계(첫 픽셀 열 = 범위 시작, 위 끝 = 축 상한 위 포함)를 단언한다. 수정을 되돌리면 이 테스트가 실패함을 확인했다.

E2E는 테스트를 약화하지 않았다. 사용자가 플롯 끝에서 정확히 드래그하면 점이 빠지는 결함이므로 기대값을 유지한다.

## 7. 사람이 재현하는 방법

### 7.1 준비(머신당 1회)

```sh
corepack pnpm -C ui install --frozen-lockfile
corepack pnpm -C ui playwright:install     # = playwright install chromium (Linux CI는 --with-deps 추가)
```

브라우저는 Playwright 캐시(Windows `%LOCALAPPDATA%\ms-playwright`, Linux `~/.cache/ms-playwright`)에 받는다.

### 7.2 E2E

```sh
corepack pnpm -C ui e2e        # vite build + Playwright E2E(Chromium), 약 1분
```

실패 시 trace·스크린샷은 `ui/test-results/e2e`, HTML 보고서는 `ui/playwright-report/e2e`에 남는다(git 제외). `ARGOS_UI_BASE_URL=http://127.0.0.1:5173`을 주면 이미 떠 있는 서버(예: `corepack pnpm -C ui dev`)를 대상으로 돈다. 이때는 CSP 헤더를 검사하지 않고(`csp-not-verified` 주석) CSP 양성 대조 5건은 건너뛴다(6.1).

`playwright test`를 직접 쓸 때(예: `corepack pnpm -C ui exec playwright test --repeat-each=3`)는 먼저 `corepack pnpm -C ui build`를 한다. 스위트는 `dist/`를 빌드 없이 서빙하므로, 전역 설정(`ui/e2e/fixtures/globalSetup.ts`, 성능 측정은 `ui/perf/lib/globalSetup.ts`)이 `dist/index.html`이 없거나 `src/**`·`index.html`·`vite.config.ts`·`package.json` 중 가장 최근 파일보다 오래되었으면 시작 전에 실패시킨다. `ARGOS_UI_BASE_URL` 대상은 검사하지 않는다.

### 7.3 프레임 시간(T-NFR-14)

조용한 머신 조건:

- 다른 프로그램을 닫고, 전원 연결, Windows 전원 모드 "최고 성능", 외부 모니터 연결 여부와 주사율을 기록한다. 측정은 Playwright가 자체 Chromium을 headless로 띄우므로 사용 중인 브라우저와 무관하다.
- 하이브리드 GPU 노트북은 측정 GPU를 고정한다. Windows 설정 → 시스템 → 디스플레이 → 그래픽에서 Playwright가 받은 Chromium 실행 파일(`%LOCALAPPDATA%\ms-playwright\chromium-<번호>\chrome-win64\chrome.exe`)을 추가하고 "절전"(내장 GPU)으로 둔다. 15 §18 #2의 기준이 저사양 노트북(내장 GPU)이기 때문이다. 그리고 `XLOG_PERF_EXPECT_GPU`에 그 GPU 이름 일부(예: `Radeon`, `Intel`)를 준다. 렌더러 문자열에 그 값이 없으면 판정 시나리오가 실패한다(비교 시나리오는 메모만 남긴다).
- 결과 md의 `GPU`·`Viewport … DPR … refresh` 행을 Gate 0 기록에 그대로 옮긴다. GPU나 주사율이 바뀌면 rAF 간격 대조값이 달라진다(4.1).

```sh
corepack pnpm -C ui perf                                 # 기본 방식(pixels, C-34), DPR 1·2 각각: 정적 1만·5만·10만, 정적 10만 최악 구성, 실시간, 상호작용, 선택 시간. 약 12~16분(부하가 높아 런마다 기다리면 40분 이상)
```

PowerShell에서 방식·옵션을 바꿀 때:

```powershell
$env:XLOG_PERF_COMPARE = '1'; corepack pnpm -C ui perf                                   # + 실시간 전체 재그리기 비교
$env:XLOG_PERF_RENDER = 'path'; $env:XLOG_PERF_SCENARIOS = 'static'; corepack pnpm -C ui perf  # path 비교(판정은 실패로 나온다)
$env:XLOG_PERF_DPR = '2'; $env:XLOG_PERF_POINT_CAP = '1.5'; $env:XLOG_PERF_SCENARIOS = 'static,static-worst'; $env:XLOG_PERF_POINTS = '100000'; corepack pnpm -C ui perf  # 점 레이어 상한 비교(4.7)
Remove-Item Env:XLOG_PERF_*                              # 원래대로
```

Git Bash·Linux: `XLOG_PERF_RENDER=path XLOG_PERF_SCENARIOS=static corepack pnpm -C ui perf`.

설정(`ui/perf/lib/settings.ts`): `XLOG_PERF_POINTS`(기본 10000,50000,100000), `XLOG_PERF_RENDER`(`default`·`path`·`rect`·`pixels`, `default` = 페이지 기본값 `pixels`), `XLOG_PERF_SCENARIOS`(기본 `static,static-worst,realtime,interaction,selection`), `XLOG_PERF_DPR`(기본 `1,2`, 1~3·소수 둘째 자리까지. 시나리오마다 `test.describe` + `test.use({ deviceScaleFactor })`로 묶이고 제목에 `dpr=<n>`이 붙는다), `XLOG_PERF_COLOR`(`status`·`instance`·`service`, 기본 `status`), `XLOG_PERF_Y`(`linear`·`log`, 기본 `linear`), `XLOG_PERF_POINT_CAP`(점 레이어 상한, 기본 페이지 값 `POINT_LAYER_MAX_DPR`), `XLOG_PERF_RUNS`(≥ 3), `XLOG_PERF_FRAMES`(120), `XLOG_PERF_WARMUP`(30), `XLOG_PERF_LIVE_SECONDS`(10), `XLOG_PERF_LIVE_RATE`(500), `XLOG_PERF_MAX_LOAD`(20), `XLOG_PERF_MAX_WAIT`(60), `XLOG_PERF_COMPARE`, `XLOG_PERF_HEADED`(1이면 창을 띄움), `XLOG_PERF_OUT`, `XLOG_PERF_RUN_ID`, `XLOG_PERF_EXPECT_GPU`(기본 없음, 대소문자 무시 부분 문자열). `static-worst`는 정적 10만 점을 y=로그 + 색 기준=서비스(13패스)로 재는 판정 시나리오이고, `selection`은 10만 점 전체 드래그 선택을 런마다 5회 해서 선택 계산·요약·React 커밋 시간을 남기는 비판정 시나리오다.

결과: 콘솔에 Markdown 표가 찍히고 `ui/perf/results/xlog-frame-<runId>.md`·`.json`·`.jsonl`과 `xlog-frame-latest.*`가 남는다. 판정 실패 시나리오는 Playwright 실패로 나온다(종료 코드 1). Gate 0 기록에는 4.7.3과 같은 표(p50/p95/max·평균·부하)와 요약표의 `Max run p95`·`Max run mean` 열을 옮기고, 런 표의 "Quiet" 열이 모두 `yes`인지 확인한다. C-35 판정은 이 두 열이 모두 16ms 이하인지로 한다. Playwright의 통과·실패는 아직 3회 합산 판정이기 때문이다(3.2). ## 8. 한계와 PM 결정 사항

결정 사항(ADR-0003)과 남은 확인:

1. **판정 통계**: ADR-0003 C-34로 결정됨. p95와 평균이 16ms 이하면 통과, max는 보고만 한다. 하네스(`checkFrameBudget`)가 이 통계로 판정한다(판정 단위는 3번).
2. **기본 그리기 방식**: ADR-0003 C-34로 결정됨. 기본값은 `pixels`이고 리뷰 r1에서 코드에 반영했다. `path`(15 §7.2의 3패스 fill, 5만·10만 점 미달)는 비교·진단용이다. 15 §7.2 "그리기" 행의 갱신은 문서 담당이다.
3. **판정 단위**: ADR-0003 C-35로 결정됨. p95·평균 판정은 런마다 적용하고(3회 런 각각이 통과해야 통과), 3회 합산 분포는 보고용이다. 공유 머신 수치는 참고값이다. 하네스의 자동 판정(Playwright 통과·실패)은 아직 합산이다. 그래서 C-35 판정은 요약표의 `Max run p95`·`Max run mean` 열로 읽는다(3.2). C-35로 보면 최적화 전 `pixels` 10만 점은 1·2차에서 미달(조용한 런 1의 p95 16.7·16.6ms), 3차에서 통과(런별 p95 최대 11.3ms)다(4.3·4.6). 리뷰 r1 반영 후 판정 런 `int-r1-final`(4.7.3)은 12건 모두 통과다(런별 p95 최대 9.8ms, 런별 평균 최대 8.2ms). 재현 런 `pmo04-final`도 모두 통과다(9.9ms, 7.9ms). 남은 확인: 조용한 머신과 저사양 기준 노트북의 Gate 0 측정(7.3).
4. **선택 계산 5ms(15 §7.3)의 판정 통계**: ADR-0003 C-36으로 결정됨. 런별 p95로 판정하고, WO-33 수락 기준으로 판정한다. 이 PoC의 값은 공유 머신 참고값이다(4.5). 판정 런은 6런 중 DPR 1 런 2 하나가 6.4ms로 넘고 나머지는 0.8~4.6ms다. 재현 런은 6런 모두 5.0ms 이하다. 런마다 5회 중 1회 튀는 값이 그 런의 p95가 되며, 튐은 DPR과 무관하다.
5. **드래그를 놓는 순간의 멈춤**: ADR-0003 C-36으로 별도 예산이 정해졌다. 드래그를 놓은 뒤 요약·목록이 화면에 반영되기까지(React 커밋 포함) p95 ≤ 100ms이고, 목록 가상화와 함께 WO-33 수락 기준으로 판정한다. 이 PoC에서 pointerup → React 커밋은 전체 선택 런별 p95 41~73ms로 예산 안이다. 그러나 커밋이 든 프레임은 뒤이은 스타일·레이아웃까지 140~313ms(상호작용 시나리오의 작은 선택, 커밋 47~104ms)라 한 번 멈칫한다. 화면 반영 기준으로는 예산을 넘을 수 있다(4.5·4.7.3). WO-33은 화면 반영 시간을 직접 재야 한다.
6. **점 레이어 상한 값**: 실측으로 `POINT_LAYER_MAX_DPR = 2`(DPR 2는 줄이지 않음)로 정했다(4.7.2). 저사양 기준 노트북(15 §18 #2)에서 DPR 2가 미달이면 1.5 또는 1로 내린다. 이 기기의 DPR 2 측정은 Gate 0 사람 확인 항목이다.

해결된 것: 캔버스 좌표 1px 결함(6.2)은 통합 단계에서 고쳤고 회귀 단위 테스트를 더했다. E2E가 통과한다.

한계:

- 수치는 공유 머신(WO-01 동시 작업)의 headless Chromium 예비 측정이고, C-35대로 참고값이다. 2차 일부 런은 "조용하지 않음"이고, 같은 코드에서도 `path` 10만 점 p50이 62~91ms로 흔들렸다. 판정 런 `int-r1-final`도 42런 중 1런이 조용하지 않았다. Gate 0 수치는 사람이 조용한 머신과 저사양 기준 노트북에서 다시 잰다.
- 프레임 시간은 trace의 스레드별 바쁜 시간으로 만든 근사다. 디스플레이 vsync 대기와 화면 합성 지연은 넣지 않는다. 1~3차와 판정 런·재현 런은 디스플레이가 144Hz라 rAF 간격이 6.9ms 단위다(GPU·주사율이 바뀌면 달라진다, 4.1).
- 1~3차는 DPR 1뿐이다. 리뷰 r1 반영 후(4.7)는 DPR 1과 2를 모두 쟀다. DPR 2에서 점 레이어는 픽셀 수가 4배라 p50이 약 1.7~1.9배가 되지만(4.7.1 opt), 최적화 후 상한 없이도 기준 안이다. DPR 2를 넘는 화면은 점 레이어를 2배로 줄인다(`POINT_LAYER_MAX_DPR = 2`, 4.7.2). DPR 2.5·3은 재지 않았다(하네스는 `XLOG_PERF_DPR=3`까지 받는다).
- 4차 실험(4.7.1·4.7.2)과 예비 판정 런 `r1cross-final1`은 이 노트북의 NVIDIA 독립 GPU(유휴 rAF 13.3ms)에서 돌았다. 1~3차의 내장 GPU 조건과 다르다. 판정 런 `int-r1-final`과 재현 런 `pmo04-final`은 1~3차와 같은 내장 Radeon(유휴 rAF 6.9ms)에서 돌았다. 15 §18 #2의 저사양 기준 노트북은 재지 않았다. Gate 0은 7.3대로 내장 GPU에 고정해 다시 잰다.
- 드래그 후 요약 + 목록 1,000행 React 커밋이 37~85ms(1~3차, 부하가 높으면 180ms) 걸린다. 판정 런에서는 전체 선택의 런별 p95가 41~73ms, 작은 선택은 47~104ms이고, 커밋이 든 프레임은 140~313ms다. 한 번 멈칫한다(위 5번). C-36 예산(화면 반영 p95 ≤ 100ms)은 WO-33에서 판정하며, 목록 가상화(WO-30 DataTable)로 해소할 것으로 본다.
- y 캐시(4.7.1)는 범위 변경·다시 그리기·실시간 프레임의 비용을 줄인다. y축 상한·선형/로그·높이·점 크기가 바뀐 첫 프레임은 모든 점의 y를 다시 계산하며, 이 한 프레임은 따로 재지 않았다(상한은 4.7.1의 pre 비용).
- 접근성: XLog 영역 선택의 키보드 대안(예: 플롯 포커스 + 화살표로 시간 밴드 이동, Enter로 선택, 또는 "보이는 범위 전체 선택" 버튼), 15 §13의 차트 대체 표, 요약 갱신 `aria-live` 알림이 없다. 플롯은 `role="img"`와 점 수 라벨만 있고 포커스를 받지 않으며, 선택은 포인터로만 만든다. 그래서 키보드만으로는 요약·목록에 도달할 수 없다(03 §3.3 키보드 주요 동작). WO-04 수락 기준 밖이라 PoC에서는 기록만 하고 WO-30(공통 접근성 패턴)과 WO-33(XLog 화면)으로 넘긴다. 차트 옵션 묶음은 `role="toolbar"`가 약속하는 키보드 패턴(화살표 이동, 탭 정지 하나)이 없어 `role="group"`으로 두었다. 정식 툴바 패턴은 WO-30 공통 컴포넌트에서 정한다.
- E2E와 성능 측정은 Chromium만 대상이다(01 문서 8장의 Edge는 같은 엔진, Firefox·Safari는 미검증, 15 §18 #8).
- Playwright가 받는 Chromium(Chrome for Testing)은 별도 프로세스로만 실행하는 개발 도구이고 산출물에 들어가지 않는다. npm 패키지(`@playwright/test`·`playwright`·`playwright-core`)는 Apache-2.0이라 `check:licenses:dev` 허용 목록 안이다. `playwright install chromium`은 Chromium과 함께 ffmpeg 빌드(`ffmpeg-<번호>`, LGPL-2.1-or-later, 영상 녹화용)와 Windows의 winldd도 받는다. 모두 사용자 캐시(`%LOCALAPPDATA%\ms-playwright` 등)에 받아 별도 프로세스로만 실행하고 저장소·산출물에 넣지 않는다. 이 브라우저 도구는 `docs/licenses/dev-only.md` 표의 `tool:playwright-browsers` 행으로 기록한다. `check:licenses:dev`는 npm 패키지만 보므로 이 행은 사람이 관리한다.
