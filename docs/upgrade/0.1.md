# Upgrading to 0.1

Argos APM 0.x makes no compatibility promise; migrations from the previous 0.x minor are provided
(see the preamble of `CHANGELOG.md`). 0.1 is the first release, so these notes are for
installations that ran a development or dogfooding build before it.

## Order: server first, then agents

Upgrade the server first. Agents follow when their applications restart, one application at a
time. The upgrade command, its backup and its rollback are in
[docs/install/compose.md, section 15.2](../install/compose.md#152-upgrade-and-rollback).

## Error groups split once

The error group fingerprint is the error class, the normalized message and the transaction's
**top application frame** (`class.method(file)`, without the line number). Agents of development
and dogfooding builds did not send that frame, so their errors were grouped by class and message
only.

- **After the agent upgrade, errors start new groups once.** An error that was one group before
  becomes a new group as soon as an upgraded agent reports it, and stays in that group afterwards.
  A redeploy that only moves lines keeps the group.
- **Changing the application packages splits the groups again.** The top application frame is the
  first frame of the stack in `instrumentation.app-packages` (derived from the main class when the
  key is unset). When you change the key, in the agent's configuration file or with a remote
  configuration change, errors that end afterwards can get another top frame and start new groups.
  Errors already recorded keep their group. Setting the key back to an empty list returns to the
  derived packages. The server's per-application packages, which only highlight frames on screen,
  do not change the groups. See
  [Application packages](../agent-config.md#application-packages).
- **Old groups stay.** They keep their history and show for time ranges before the change; they
  get no new occurrences and leave the error statistics with the retention of those statistics.
- **What you see.** Right after the change, the error statistics show the same errors under new
  groups with the **New** badge, so the **New only** filter lists more groups than usual for one
  time range. The error counts and the error rate do not change. No alert rule in 0.1 watches new
  error groups (the metric `error_group_new` has no value in this version), so no Argos alert fires
  because of the split; review any process of your own that counts new groups.

What to do:

1. Note the time of the agent upgrade or of the packages change, like a deployment marker. A
   remote configuration change is in the audit log with its time and reason
   (`CONFIG_CHANGE_CREATED`, `CONFIG_CHANGE_APPLIED`); a change of the local file is not, so record
   it yourself. To mark it on the charts, add an event of type `custom` (`POST /api/v1/events`, see
   `docs/api/openapi.yaml`), for example from the deployment pipeline with an agent token of the
   application.
2. When you compare error groups across that time, compare by error class and message, not by group.
3. If you forward new error groups to people (a report or a script of your own), pause it briefly
   or tell its readers about the one-time split.
